# Plan: Greenfield Single Repository for Laravel, Vite React, and Expo Apps

## Summary
Create a greenfield single repository containing three independent root-level applications: a Laravel PHP backend in `backend/`, a Vite-powered React web app in `web/`, and a React Native mobile app using Expo in `mobile/`. The plan uses a no-workspace structure: each app owns its own dependencies, scripts, environment files, tests, build commands, and release workflow. Root-level documentation, ignore rules, CI, and deployment guidance tie the repository together without adding workspace tooling or root-level package orchestration.

## Phase 1: Repository Foundation
**Agent:** dev
**Files:** `README.md` (modify), `.gitignore` (create)

Establish the greenfield repository foundation with fixed root-level application directories. Keep the repository simple and avoid workspace tooling or task-runner setup.

### Steps
1. Use the root-level directory layout: `backend/`, `web/`, and `mobile/`.
2. Create a root `.gitignore` that covers common Laravel, PHP, Node, Vite, Expo, React Native, IDE, OS, build, cache, and environment-file artifacts.
3. Add a repository overview to the root README explaining that the repo contains three independent applications in one repository.
4. Document that each app must be installed, run, tested, and built from its own directory.
5. Document that no root JavaScript package manager configuration, workspace file, or root task runner is part of the initial setup.

### Acceptance Criteria
- The repository has a root `.gitignore` suitable for a Laravel + Vite React + Expo greenfield repo.
- The README records the root-level structure: `backend/`, `web/`, and `mobile/`.
- The README makes clear that the repository does not use workspaces or root-level task orchestration.
- No shared package directory, workspace configuration, or root package manager orchestration is introduced.

## Risks and Mitigations
- **Independent app setup can lead to duplicated commands.** Mitigate by documenting app-specific commands clearly in the README and keeping each app's scripts close to the app that owns them.
- **PHP and JavaScript ecosystems have different dependency, cache, and CI needs.** Mitigate by keeping Laravel Composer workflows separate from Node package manager workflows and using app-specific CI jobs.
- **Environment variables differ across Laravel, Vite, and Expo.** Mitigate by documenting separate `.env.example` files and naming conventions: Laravel server-side variables, Vite `VITE_` variables, and Expo `EXPO_PUBLIC_` variables where appropriate.
- **Deployment targets are split by runtime.** Mitigate by documenting backend, web, and mobile release paths independently instead of assuming a single deployment platform.
- **Expo and Vite may use different Node/package manager versions over time.** Mitigate by documenting required runtime versions per app and keeping lock files inside each app directory.
- **Root-level convenience tooling can creep into the repository.** Mitigate by treating any future root-level orchestration proposal as a separate decision after the three independent apps are stable.
